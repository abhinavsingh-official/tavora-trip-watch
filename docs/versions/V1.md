# Version 1 — the skeleton

*Template used for every version doc from here on: what it does, what's new, what's
active, what's real vs simulated, what the Scenario Lab can do at this stage, stress
tests run, decisions made, and honest gaps. See `docs/DECISIONS.md` for the reasoning
behind any choice referenced here.*

## 1. What this version does

One mock user (User A — Mumbai ⇄ Goa, 2 adults, 3 nights, 1 room, ₹35,000 budget),
one request, one path, by hand: create the request → press "check price now" → see
an itemized total → if it's under budget, see one in-app notification → open it,
see the price re-checked, explicitly say "book it" → see a simulated booking result
for all three components. Happy path only — nothing is deliberately broken yet.

## 2. What's new since the last version

Everything — this is the first version.

## 3. Architecture active this version

- **Backend**: FastAPI, single process.
- **Database**: Postgres, real schema from day one (not SQLite — see
  `DECISIONS.md`'s database section for why), but only the tables V1 actually needs:
  `users`, `trip_requests`, `price_observations`, `notifications`, `booking_attempts`.
- **Frontend**: React + Vite + TypeScript, calling the backend over HTTP.
- **Scheduler**: not active yet — V1 only has the manual "check now" button. The
  5-minute automatic cycle is V2.
- **Scenario Lab**: active at `/lab`, minimal — a clock display + a per-component
  price override. Failure injection, inventory control, and the one-click scenario
  buttons arrive in V2+ as there's more to break.

## 4. Data sources used

Flights will call **Sabre Dev Studio** for real — registration, auth, and a real
Bargain Finder Max v4 call for BOM→GOI are all confirmed working (round 9,
`docs/NOTES.md`). Hotels (Hotelbeds, pending registration) and cabs (no viable real
source exists — see `research_summary.md` §6.4/§7.3) stay simulated in V1. "Real"
here means a real sandbox contract with schedule-realistic data and test-cell
fares (not live market prices) — the same honest distinction drawn for Duffel
throughout this project's research.

| Component | Source this version | What's actually computed |
|---|---|---|
| Flight (outbound + return) | **Real sandbox** — Sabre Bargain Finder Max v4 (confirmed working, round 9) | A real BOM↔GOI itinerary query against Sabre's cert environment; schedule/carrier data is real, fares come from Sabre's static test cell (not live prices) |
| Hotel (room-nights) | Simulated (Hotelbeds registration in progress) | A per-night rate for the requested star category, multiplied by nights and room count |
| Cab (both airport transfers) | Simulated | Modeled as a fixed-quote transfer (per `research_summary.md` §6.4.2/§6.4.3's Kiwitaxi/Savaari-shaped finding, not a surge multiplier), with vehicle class selected by adult count — sedan-class for ≤3 adults, a larger-vehicle rate anchored to the real ₹20–28/km tempo-traveller market range for 4+ adults |

Flights are the one component with a real sandbox call wired in from V1; hotels and
cabs stay simulated, for the distinct reasons documented in `research_summary.md`
§7.2/§7.3 (see §8 below for the honest gap this still leaves).

## 5. Simulation controls available this version

- View the current simulated time (real-mode clock, not yet advanceable in the UI —
  advancing is only meaningful once holds/cycles exist in V2).
- Override the next price for a specific component on a specific request, so "it
  alerts when under budget" can be demonstrated without waiting for a naturally cheap
  simulated price.

## 6. Stress tests run + results

None yet in a formal sense — V1 is the happy path by design. The one check performed
manually before calling V1 done: create the request, confirm the itemized total adds
up correctly (flight + hotel + both transfers + tax, nothing silently dropped), and
confirm the booking result shows all three components as a distinct line each, not
one lump sum.

## 8. Honest gaps — deferred to V2 and why

- **No automatic 5-minute scheduler yet** — V1 only proves the pricing/alert/booking
  logic works when triggered; making it run on its own is a V2 correctness concern,
  not a V1 one.
- **No alert state machine** (first-crossing / 5%-re-alert / above-budget-reset) —
  V1 sends at most one notification per request, period. The real state machine is
  V2's core focus.
- **No real hold/expiry countdown** — V1's "booking" doesn't actually hold components
  for 2 minutes with an expiring timer; it re-checks the price once and books
  immediately on consent. Real holds are V2.
- **No failure handling** — nothing in V1 can fail, time out, or partially book.
  That's the explicit subject of V2.
- **Hotelbeds/RateHawk integration for hotels** — registration in progress; hotels
  stay simulated until a key is confirmed working the same way Sabre now is.
  Cabs have no viable real source at all (see `research_summary.md` §6.4/§7.3) and
  will stay simulated through all versions on current evidence.
- **Only one mock user** — Users B and C (and the occupancy/room-count stress they
  bring) are V3.
