# Version 1 — the skeleton

*Template used for every version doc from here on: what it does, what's new, what's
active, what's real vs simulated, what the Scenario Lab can do at this stage, stress
tests run, decisions made, and honest gaps. See `docs/DECISIONS.md` for the reasoning
behind any choice referenced here.*

## 1. What this version does

One mock user (User A — Mumbai ⇄ Goa, 2 adults, 3 nights, 1 room, ₹35,000 budget),
one request, one path, by hand: create the request → press "check price now" → see
an itemized total → if it's under budget, see one in-app notification → open it,
see the price re-checked, explicitly say "book it" → see a simulated booking result
for all three components. Happy path only — nothing is deliberately broken yet.

## 2. What's new since the last version

Everything — this is the first version.

## 3. Architecture active this version

- **Backend**: FastAPI, single process.
- **Database**: Postgres, real schema from day one (not SQLite — see
  `DECISIONS.md`'s database section for why), but only the tables V1 actually needs:
  `users`, `trip_requests`, `price_observations`, `notifications`, `booking_attempts`.
- **Frontend**: React + Vite + TypeScript, calling the backend over HTTP.
- **Scheduler**: not active yet — V1 only has the manual "check now" button. The
  5-minute automatic cycle is V2.
- **Scenario Lab**: active at `/lab`, minimal — a clock display + a per-component
  price override. Failure injection, inventory control, and the one-click scenario
  buttons arrive in V2+ as there's more to break.

## 4. Data sources used

Flights call **Sabre Dev Studio** for real — registration, auth, and a real
Bargain Finder Max v4 call for BOM→GOI are all confirmed working (round 9,
`docs/NOTES.md`). Hotels call **Hotelbeds** for real too — registration, auth,
and real Goa coverage are all confirmed working (round 10/11): Goa's real
destination code is `GOO`, and a geolocation search returned 11 real, named,
independently-verifiable hotels (Kenilworth Beach Resort, The Zuri White Sands
Goa Resort & Casino, Regenta Baywatch Resort Goa, others), with currency
confirmed EUR and converted to INR at a documented, labeled fixed rate. Whether
the underlying fare numbers are live or test-cell remains the one open check
(see §8). Cabs have no viable
real source at all (see `research_summary.md` §6.4/§7.3) and stay simulated.
"Real" throughout means a real sandbox contract with real catalog/inventory
data, not necessarily confirmed-live market prices — the same honest distinction
drawn for Duffel throughout this project's research.

| Component | Source this version | What's actually computed |
|---|---|---|
| Flight (outbound + return) | **Real sandbox** — Sabre Bargain Finder Max v4 (confirmed working, round 9) | A real BOM↔GOI itinerary query against Sabre's cert environment; schedule/carrier data is real, fares come from Sabre's static test cell (not live prices) |
| Hotel (room-nights) | **Real sandbox** — Hotelbeds geolocation search, destination code `GOO` (confirmed working, round 11; currency confirmed round 13) | A real availability query against Hotelbeds' test environment for Goa; 11 real, named hotels returned with real room types/board types/cancellation policies; currency confirmed `EUR` via a real `CheckRates` call, converted to INR with a documented fixed rate, clearly labeled as approximate — whether the EUR fare numbers themselves are live or test-cell is not separately confirmed |
| Cab (both airport transfers) | Simulated | Modeled as a fixed-quote transfer (per `research_summary.md` §6.4.2/§6.4.3's Kiwitaxi/Savaari-shaped finding, not a surge multiplier), with vehicle class selected by adult count — sedan-class for ≤3 adults, a larger-vehicle rate anchored to the real ₹20–28/km tempo-traveller market range for 4+ adults |

Flights and hotels both have real sandbox contracts confirmed reachable with
real data for this project's actual route; cabs stay simulated, for the reasons
documented in `research_summary.md` §6.4/§7.3 (see §8 below for the honest gap
this still leaves on the hotel-pricing side).

## 5. Simulation controls available this version

- View the current simulated time (real-mode clock, not yet advanceable in the UI —
  advancing is only meaningful once holds/cycles exist in V2).
- Override the next price for a specific component on a specific request, so "it
  alerts when under budget" can be demonstrated without waiting for a naturally cheap
  simulated price.

## 6. Stress tests run + results

None in the deliberate break-it-on-purpose sense yet — that's V2+, once there's a
failure path to break. What was verified by a real, live run of the actual backend
before calling the happy path done:

- Seeded User A's real request, called `check` — got real Sabre flight prices and a
  real Hotelbeds hotel price (EUR→INR converted), plus the simulated cab fares, all
  itemized correctly: ₹7,492 + ₹7,186 (flights) + ₹16,435.95 (hotel) + ₹900 + ₹900
  (cabs) + ₹1,645.70 (tax) = ₹34,559.65 — under User A's ₹35,000 budget, nothing
  silently dropped or double-counted.
- Confirmed exactly one notification was created (not zero, not more than one).
- Called `review` — got a fresh observation with the same total (Sabre/Hotelbeds
  test-cell data is deterministic, as expected), original and current totals both
  returned for comparison.
- Called `book` — got all three components `confirmed` with three distinct fake
  supplier references, not one lump sum.
- Confirmed the raw Sabre/Hotelbeds API responses are actually persisted on the
  observation row, not discarded after extracting the price.
- Confirmed a Scenario Lab price override on `flight` actually changes what the next
  `check` returns, and `/api/lab/reset` clears it.
- Confirmed ownership scoping actually blocks User B from reading User A's request
  by ID (404, not someone else's data).
- **Frontend verified with a real headless-browser run**, not just a clean
  build: Dashboard → Check price now → Notifications → Offer Review → Confirm
  booking → Booking Result → Scenario Lab, end to end against the live
  backend, zero browser console errors. This run itself caught two real bugs
  (a Lab override double-counting the return leg; `reset.py` claiming to reset
  state it can't reach across processes) - both fixed and logged as their own
  PRs before this version was called done.
- **A deliberate pre-deploy hardening pass** (2026-11-22, see `DECISIONS.md`)
  found and fixed nine more real issues, each verified with a real test:
  booking had no idempotency guard (fixed app-level + a DB unique constraint
  + race handling, verified by booking the same notification three times
  through the real app and getting the same booking back); the exact same
  race existed in notification creation (fixed with a transaction-scoped
  Postgres advisory lock, verified by firing 15 concurrent real checks and
  getting exactly 1 notification, not more); real supplier failures were
  being silently swallowed with zero logging; there was no caching, so every
  check cost real quota (fixed with a 4-minute TTL cache - verified a
  repeat check dropped from ~7.6s to ~0.03s); no rate-limiting
  respected Hotelbeds' documented burst limit; Sabre's token cache had a
  concurrency race; several foreign-key columns had no indexes; the frontend
  had no production API base URL (would have 404'd on a split deploy); and
  two frontend unhandled-promise-rejection gaps left failures invisible.

## 8. Honest gaps — deferred to V2 and why

- **No automatic 5-minute scheduler yet** — V1 only proves the pricing/alert/booking
  logic works when triggered; making it run on its own is a V2 correctness concern,
  not a V1 one.
- **No alert state machine** (first-crossing / 5%-re-alert / above-budget-reset) —
  V1 sends at most one notification per request, period. The real state machine is
  V2's core focus.
- **No real hold/expiry countdown** — V1's "booking" doesn't actually hold components
  for 2 minutes with an expiring timer; it re-checks the price once and books
  immediately on consent. Real holds are V2.
- **No failure handling** — nothing in V1 can fail, time out, or partially book.
  That's the explicit subject of V2.
- **Hotelbeds — fare realism, not currency, is the remaining gap** — currency is
  confirmed EUR (round 13, via a real `CheckRates` call) and V1 converts it to
  INR with a documented fixed rate, clearly labeled as approximate. Whether the
  underlying EUR numbers are live or from a static test cell (the same
  distinction already drawn for Sabre) hasn't been separately confirmed. RateHawk
  is settled (Reject — gated, no INR data), not an open option.
  Cabs have no viable real source at all (see `research_summary.md` §6.4/§7.3) and
  will stay simulated through all versions on current evidence.
- **Only one mock user** — Users B and C (and the occupancy/room-count stress they
  bring) are V3.
- **`raw_sources` has no pruning/archival policy** — the full raw Sabre/Hotelbeds
  response is stored on every observation, forever. Deliberately not fixed in
  the pre-deploy hardening pass (see `DECISIONS.md`) - an actual retention
  policy is a real design decision that deserves consideration once V2's
  scheduler exists and the growth rate is real, not a reflexive fix today.
