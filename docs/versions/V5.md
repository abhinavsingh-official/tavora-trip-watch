# Version 5 — UI pass

*Same template as V1.md-V4.md. See `docs/DECISIONS.md` for the reasoning
behind any choice referenced here, and `docs/UI_PLAN.md` for the planning
that preceded this version (now folded in here as the shipped record).*

## 1. What this version does

Replaces the plain, unstyled-HTML look of every real page with a real
design system (consistent tokens, cards, buttons, status pills) and two
structural layout changes borrowed directly from a real frontend reference
survey: a grouped, sectioned request form, and a sticky summary-card-with-
CTA pattern on the Request Form and Offer Review pages. No new product
behavior - every change here is visual/structural, not a feature.

## 2. What's new since V4

- `frontend/src/styles.css` rewritten around CSS custom-property design
  tokens (color, spacing, radius, shadow) instead of one-off values.
- Inter (Google Fonts) in place of the system font stack; page `<title>`
  fixed (was literally "frontend").
- App header restyled as pill-tab navigation with a sticky top bar; a
  responsive breakpoint added (nav previously overflowed the viewport on a
  390px-wide screen - a real bug found during this pass, not present
  before since nothing was tested below desktop width).
- Request Form: grouped into three sectioned cards (Route & dates;
  Travellers & stay; Budget & flight preferences), an origin/destination
  swap button, and a live sticky "Trip summary" card carrying the
  Create/Save action - mirroring Google Flights' grouped-card search form
  and Tavora's own trip-wizard summary pattern (`docs/UI_PLAN.md`).
- Offer Review: two-column layout - itemized total on the left, a sticky
  "Your offer" summary card on the right with the hold countdown and the
  Confirm action, same pattern as the Request Form.
- Status values render as colored pill badges everywhere (including the
  five new V4 states - `needs_reconciliation`, `manual_intervention`,
  `in_progress`, `cancellation_failed`, `unknown`).
- Scenario Lab: full copy rewrite (the "worded weirdly" feedback) - plainer
  language throughout, one shared "target request ID" field instead of
  four duplicated ones, buttons renamed from "Arm X" to "Schedule X".
  Visually kept in a deliberately different register (dashed card borders)
  so it still reads as dev tooling, not a real product screen.
- Dashboard, Notifications, Ops, Booking Result: visual polish only
  (cards, pills, spacing) - no structural change, since their existing
  list/detail shape didn't need one.

Unchanged from V4.

## 6. Stress tests run + results

- `npm run build` - clean, before and after every structural change.
- Real headless-browser screenshots of every page (Dashboard, Request
  Form, Notifications, Ops, Lab, Offer Review, Booking Result), reviewed
  directly, not assumed to look correct from the markup alone.
- **Found and fixed two real bugs this way, not caught by the build**: (1)
  a CSS specificity bug where `.form-grid` and `.field-swap-row`'s grid
  layouts were silently overridden by the generic `.form` flex rule
  appearing later in the stylesheet on the same element - fixed by
  combining selectors (`.form.form-grid`) rather than relying on source
  order; (2) the app header had no responsive behavior at all and
  overflowed the viewport horizontally at a 390px mobile width - fixed
  with a breakpoint that wraps the nav onto its own row.
- A full real flow exercised end to end through the new UI, not just
  static pages: created a request, triggered a real price check (real
  Sabre/Hotelbeds calls), reviewed the resulting offer, and confirmed a
  real simulated booking - all the way to a `confirmed` Booking Result
  page, screenshotted at each step.
- Console-error check across all seven real pages (Dashboard, Request
  Form, Notifications, Ops, Lab, Offer Review, Booking Result) - zero
  errors.
- `backend/.venv/bin/python -m pytest -q` - 32 passed (no backend changes
  this version; re-run as a sanity check, not because anything here could
  plausibly affect it).

## 8. Honest gaps — what's left

- The real frontend reference survey didn't capture ixigo's actual Fare
  Alerts/Smart Lock screens (blocked by rate-limiting) - the closest real
  competitor analog to this product's own feature. Not reachable this
  round; the design decisions made here didn't end up depending on it.
- No dark mode, despite the `styles.css` tokens being structured in a way
  that could support one later (CSS custom properties, no hardcoded colors
  outside `:root`) - not asked for, not built.
- Still no icon set/illustration - deliberately kept to typography, color,
  and spacing only, consistent with Sec. 10/15's own "polish is secondary"
  priority; no new dependency was added to get this version's result.
