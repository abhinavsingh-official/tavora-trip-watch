# Version 3 — breadth

*Same template as V1.md/V2.md. See `docs/DECISIONS.md` for the reasoning
behind any choice referenced here.*

## 1. What this version does

Stretches the now-correct core loop (V1+V2) to actually match the brief's
required scope: all three mock users, not one; a request can be edited,
paused, cancelled, and reactivated, with editing invalidating any stale held
offer; a real automated test suite covers the three things most likely to
silently break; and the operations view (one of §10's six required screens,
not Lab tooling) surfaces anything stuck in a non-confirmed state with a
real event timeline.

## 2. What's new since V2

- Users B (Delhi⇄Goa, 4 adults, 2 rooms, ₹65,000) and C (Mumbai⇄Jaipur, 2
  adults, 1 room, ₹30,000) seeded with their real requests from Sec. 02.
- `PATCH /api/requests/{id}` (edit), `POST .../pause`, `POST .../cancel`,
  `POST .../reactivate` - all owner-scoped.
- Editing invalidates any un-booked held offer on that request (clears
  `held_observation_id`/`held_until`) and resets `last_alerted_total`, so the
  alert state machine starts clean against the edited numbers.
- Manual "check price now" now requires `status == "active"` - paused/
  cancelled requests reject it with a clear message. The scheduler already
  only processes active requests (unchanged from V2).
- A real pytest suite (`backend/tests/`): pricing itemization math, the full
  alert state machine (first-crossing/re-alert/reset/failed-check-does-
  nothing), and ownership scoping across every affected endpoint.
- `GET /api/ops/partial-bookings` + `GET /api/ops/requests/{id}/timeline` -
  the real operations screen, scoped per user like every other real screen.
- Frontend: edit mode on the request form, pause/cancel/resume buttons and a
  status badge on the Dashboard, and a new Ops page.

## 3. Architecture active this version

Unchanged from V2 - same scheduler, same alert state machine, same hold
mechanism. V3 adds breadth around it, not new core mechanisms.

## 4. Data sources used

Same three sources as V1/V2. Notably: **User C's Mumbai⇄Jaipur request is
the first real call against Jaipur's Hotelbeds coordinates**, which had been
hardcoded since round 11 but never independently verified - confirmed real
this version (see `docs/NOTES.md` round 14). User B's 4-adult/2-room request
is the first real call that exercises Hotelbeds' multi-room occupancy
pricing - verified correct by inspecting the raw response directly, not just
trusting the extracted number.

## 5. Simulation controls available this version

Unchanged from V2 (clock advance, price override, failure injection, trigger
cycle). V3 doesn't add new Lab levers - it adds real product screens instead.

## 6. Stress tests run + results

- **User B (occupancy math)**: real check returned a real combined 2-room/
  4-adult hotel rate (`Soul Vacation Resort and Spa`, raw response explicitly
  tagged `"rooms": 2, "adults": 4"`) and the correct tempo-traveller cab rate
  (₹720/leg, not the ≤3-adult sedan rate of ₹900/leg) - both confirmed by
  inspecting real data, not assumed from the code.
- **User C (Jaipur)**: real check returned a real hotel result, settling
  Jaipur's previously-unverified coordinates.
- **Edit invalidation**: reviewed an offer (real hold established), edited
  the request's budget, confirmed the hold was cleared
  (`held_until` → `null`), confirmed a subsequent booking attempt was
  correctly rejected with "no active hold."
- **Status gating**: paused a request, confirmed a manual check was rejected
  with a 400; reactivated it, confirmed checks worked again; confirmed a
  cancelled request cannot be reactivated.
- **Ops view**: forced a real partial-failure booking (same mechanism as
  V2's stress test), confirmed it appeared in the partial-bookings list, and
  confirmed its event timeline correctly reconstructed and time-ordered five
  real events (observation → alert → re-check → review → partial booking)
  from three separate tables.
- **Automated suite**: 17 tests, all passing, covering pricing math (3
  tests), the alert state machine (7 tests, mirroring every manual scenario
  from V2's own stress-testing), and ownership scoping (7 tests, covering
  check/review/book/observations/edit). Verified reproducible: a completely
  fresh test database, run twice in a row, passes identically both times.
- **Full real headless-browser run**: Dashboard across all three users, a
  real check for each, edit/pause/resume, and the Ops page both empty and
  populated with a real partial booking. Zero console errors.
