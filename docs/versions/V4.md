# Version 4 — closing the remaining gaps

*Same template as V1.md/V2.md/V3.md. See `docs/internal/decision-log.md` for the
reasoning behind any choice referenced here.*

## 1. What this version does

Closes the three honest gaps V3 explicitly carried forward: the remaining
five of six Sec. 09 booking failure-table rows, Sec. 11 scenario 6
(timeout + restart), and Sec. 12's 100-request load demonstration.

## 2. What's new since V3

- Booking now persists incrementally - each component's outcome commits
  individually, not just the final result - which is what makes "resume
  after a simulated restart" possible.
- New Scenario Lab levers: a booking-failure `outcome` (`fail` /
  `unavailable` / `timeout`), a cancellation-failure injector, and a
  "restart after this component" injector.
- New `POST /api/bookings/{id}/reconcile` endpoint - the only way a
  `needs_reconciliation` booking (a simulated supplier timeout) moves
  forward.
- New booking/aggregate status values: `unknown`, `cancellation_failed`,
  `needs_reconciliation`, `manual_intervention`, `in_progress` - all new
  string values in the existing columns, zero schema changes.
- `backend/tests/test_booking.py` - 10 new tests covering idempotency, both
  new forced outcomes, reconcile in both directions, restart-resume, and
  cancellation failure.
- `backend/scripts/load_test.py` - the real, reproducible 100-request/
  3-cycle load demonstration against a simulated supplier.
- Frontend: Booking Result shows a reconcile action when stuck, an
  in-progress/manual-intervention explanation, and the Scenario Lab gained
  three new control cards.

## 3. Architecture active this version

Unchanged - same scheduler, same alert state machine, same hold mechanism,
same database schema (no migration needed; see `docs/internal/decision-log.md`). V4
adds depth to the booking workflow's recovery behavior, not new mechanisms.

## 4. Data sources used

Unchanged from V3. The load test explicitly does **not** call Sabre/
Hotelbeds/cabs - it patches `app.monitoring.build_package` with a
deterministic simulated supplier, per the assignment's own instruction not
to generate unnecessary load against real services.

## 5. Simulation controls available this version

Builds on V2/V3's Scenario Lab: `fail-component` now takes an `outcome`
(`fail`/`unavailable`/`timeout`), plus two new one-shot levers,
`cancel-failure` and `restart-after`. All consumed (popped) by the very
next booking attempt on that request, same one-shot discipline as every
existing lever.

## 6. Stress tests run + results

- **Automated suite**: 27 tests passing (17 carried from V3 + 10 new
  booking tests), run fresh via `.venv/bin/python -m pytest -q`.
- **Live verification against a real running local server** (not just
  pytest), each with real observations/notifications inserted and real HTTP
  calls:
  - Forced `timeout` on hotel → booking returned `needs_reconciliation`
    with `hotel_status="unknown"`; a second `book()` call returned the
    identical stuck row (no new attempt); `POST .../reconcile` with
    `outcome=confirmed` resolved it and booked the remaining `cab`
    component, final `aggregate_status="confirmed"`.
  - Forced `restart_after=flight` → booking stopped after flight confirmed,
    `aggregate_status="in_progress"`; a second `book()` call on the same
    notification resumed and finished hotel+cab with the same
    `BookingAttempt` id - no duplicate row.
  - Forced `fail` on hotel + `cancel-failure` on flight → result was
    `flight_status="cancellation_failed"` (supplier ref preserved, not
    erased), `aggregate_status="manual_intervention"`.
  - Ops view (`/api/ops/partial-bookings`) correctly surfaced the
    `manual_intervention` booking and correctly stopped surfacing the two
    bookings that were resolved back to `confirmed`.
- **100-request load demonstration**, real run via
  `backend/scripts/load_test.py`: 3 cycles of 100 active requests, ~0.7s per
  cycle (~7ms/request), 0 errors, 0 duplicate alerts across any request, 40
  notifications created (matching the deterministic fixture's intended
  alerting population - even-numbered, non-multiple-of-10 request IDs -
  exactly). Linear extrapolation to 1,000 requests: ~7.3s/cycle - see
  `docs/VERIFICATION_PACKAGE.md` §3 for the full report, including why this
  architecture would need to change well before that scale in practice
  (Hotelbeds' real 50/day quota, not raw compute, is the actual ceiling).
