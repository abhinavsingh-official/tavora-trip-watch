# Version 2 — the core loop made correct and safe

*Same template as V1.md. See `docs/internal/decision-log.md` for the reasoning behind any
choice referenced here, and `docs/versions/V1.md` for what V1 already covers.*

## 1. What this version does

Takes V1's one-shot happy path and makes it behave the way a real system has
to: prices are watched automatically, not just on demand; an alert fires on
real rules (first crossing, re-alert only on a further 5% drop, silent reset
above budget), not "at most once ever"; a reviewed offer's price is actually
frozen for 2 minutes and an expired hold is rejected, not silently honored;
and one real booking-failure scenario — a component failing after another
already succeeded — triggers a real compensating cancellation, not a
best-case assumption.

## 2. What's new since V1

- A real 5-minute automatic monitoring cycle (APScheduler, in-process),
  alongside the manual "check price now" button - both call the exact same
  alert logic (`app/monitoring.py`), not two copies that can drift.
- The real alert state machine (Sec. 07), backed by a new
  `trip_requests.last_alerted_total` column.
- Real holds: `notifications.held_observation_id` + `held_until`, set when
  an offer is reviewed, enforced server-side when booking is attempted.
- The server now derives the booked total from the held observation itself,
  not from whatever the client sends — a real correctness tightening over
  V1, which trusted the client's number.
- One real failure scenario: a Scenario-Lab-forced component failure during
  booking triggers a compensating cancellation of whatever already
  succeeded, with a real `partial` aggregate status.
- Three new Scenario Lab levers: advance the sim clock, force a component to
  fail on the next booking attempt, and trigger a monitoring cycle on demand.
- A real, significant bug fixed mid-build, not just a feature added: every
  timestamp this app returns is now timezone-aware with an explicit UTC
  offset — found by an actual browser test showing a brand-new 2-minute hold
  as already expired (see §6 and `DECISIONS.md`).

## 3. Architecture active this version

- **Scheduler**: `app/scheduler.py`, an in-process APScheduler
  `BackgroundScheduler`, one job every 5 minutes, started/stopped via
  FastAPI's lifespan. Known limitation, already documented in `DECISIONS.md`'s
  deploy entry: on Render's free tier this stops ticking while the service is
  asleep, since it's not a separate worker process.
- **Alert state machine**: `app/monitoring.py` — `run_check_and_alert`,
  called identically by the manual endpoint and the scheduler. Still uses
  V1's per-request Postgres advisory lock, now guarding the richer state
  machine instead of the simple "has any notification ever existed" check.
- **Holds**: set in `routers/notifications.py`'s review endpoint, enforced in
  `routers/booking.py` before any booking logic runs.
- **Scenario Lab**: `/lab` gains clock-advance, failure-injection, and
  trigger-cycle controls — all real, reachable endpoints, same philosophy as
  V1's price overrides.

## 4. Data sources used

Unchanged from V1 — Sabre (real sandbox) for flights, Hotelbeds (real
sandbox, EUR→INR converted) for hotels, simulated cabs. V2 is entirely about
correctness of the loop around those prices, not the prices themselves.

## 5. Simulation controls available this version

- Everything from V1 (clock display, price overrides).
- **Advance the sim clock** by N minutes — the literal "replay without
  waiting for real time to pass" requirement (Sec. 11).
- **Force a component to fail** on the next booking attempt for a request —
  one-shot, consumed by that attempt.
- **Trigger a monitoring cycle now** — runs the real scheduler job
  immediately instead of waiting up to 5 real minutes.

## 6. Stress tests run + results

All four new mechanisms verified with real requests against a real running
server, not just read through:

- **Alert state machine**: first check under budget → exactly 1 notification.
  Same price checked again → still 1 (no re-alert on a non-drop). Forced a
  real ~42% price drop via a Lab override → re-alert fired (2nd
  notification). Forced the price back above budget → notification count
  stayed at 2 (silent reset, confirmed no notification created). Forced back
  under budget → a 3rd notification appeared, confirmed treated as a first
  crossing, not a re-alert.
- **Holds**: reviewed an offer, booked immediately within the hold → booking
  succeeded, using the server-derived held total. Reviewed a fresh offer,
  advanced the sim clock 3 minutes past the 2-minute hold, attempted to
  book → rejected with a real 409, "hold expired." Attempted to book a
  notification that had never been reviewed at all → rejected with a 400,
  "no active hold."
- **Partial-failure scenario**: armed a forced hotel failure via the Lab,
  booked a held offer → flight confirmed then compensated to `cancelled`,
  hotel `failed`, cab never attempted and correctly stayed `pending`,
  aggregate `partial`. Called `book` again on the same notification →
  returned the identical partial result (idempotency guard from V1 still
  holds under the new, more complex booking logic).
- **A real bug found and fixed by this exact process**: the hold-expiry test
  above initially failed in a browser (not via curl) — a brand-new hold
  showed as already expired. Root cause: every timestamp was naive UTC with
  no offset marker, which a browser outside UTC (this one, IST) silently
  misread as local time. Fixed by switching every `DateTime` column to
  `DateTime(timezone=True)` and every clock read to
  `datetime.now(timezone.utc)` — re-verified in a real browser afterward,
  confirmed correct ("Price held for 119s").
- **Full real headless-browser run** of the whole new surface: check price →
  offer review showing a live countdown → Scenario Lab arming a hotel
  failure → booking → partial result rendered with the right status colors
  for `cancelled`/`failed`/`pending` (new CSS states, previously unused).
  Zero console errors.

## 8. Honest gaps — deferred to V3 and why

- **Only the "one component fails after another succeeds" scenario is
  built.** The other five failure-table rows from Sec. 09 follow the same
  shape (don't lie about what happened, don't do the same thing twice) —
  understood and explainable, not independently implemented. Building all
  six wasn't the point of V2; building one, correctly, was.
- **Still only one mock user.** Users B and C, and the occupancy/room-count
  stress they bring, are V3.
- **No automated test suite yet.** Everything in §6 was verified by hand
  against a real running server — real evidence, but not a reusable,
  CI-runnable suite. That's V3's job (Sec. 12).
- **The production database schema change for V2** (the new columns) was
  applied by a full reset of the deployed database, not a non-destructive
  migration — acceptable here since it only held seed/test data, not
  anything real, but worth being explicit that this project has no real
  migration tooling (Alembic or similar) yet.
