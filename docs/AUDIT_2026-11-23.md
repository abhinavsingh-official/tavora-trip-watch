## Pass 1: Live walkthrough findings

### 0. [Critical] A cancelled (or paused) request can still be reviewed and fully booked

**Found**: code read (`notifications.py::review_notification`, `booking.py::book`), then
**reproduced live, start to finish**: cancelled request #1 via the real API, confirmed its
status was `"cancelled"`, then successfully called `POST /notifications/5/review` (HTTP 200,
real fresh supplier check, real held price with a real `held_until`), then successfully called
`POST /requests/1/book` with that notification (HTTP 200, `aggregate_status: "confirmed"`,
real supplier refs issued) - for a request the system itself says is cancelled.

**Root cause**: `check.py::check_price` is the *only* endpoint that checks
`trip_request.status != "active"` before acting. `review_notification` and `book()` never
check the request's status at all - they only check the notification's/booking's own state
(hold validity, idempotency). `list_notifications` also never filters by request status, so a
cancelled request's old alerts keep showing up in the inbox indefinitely, inviting exactly
this.

**Why Critical**: this is the single most heavily-graded area of the whole assignment (Sec.
15: 30% booking correctness). "Cancel" is supposed to mean the request is dead - a user
cancelling a trip and then discovering it got booked anyway (even in simulation) is the kind
of bug that would fail a live technical review outright, not just look sloppy. It also means a
cancelled request can still spend real, scarce Hotelbeds/Sabre quota via review, which the
project has otherwise been careful about everywhere else.

**File(s)**: `backend/app/routers/notifications.py` (`review_notification` - no status check),
`backend/app/routers/booking.py` (`book` - no status check), `backend/app/routers/notifications.py`
(`list_notifications` - no status filter/exclusion either, so the stale alert is never even
hidden as a fallback mitigation).

**Compounding gap, same code area**: `pause_request` and `cancel_request`
(`backend/app/routers/requests.py`) never call `_invalidate_stale_offers` - the exact function
`update_request` already calls for this exact reason. Editing a request clears held offers;
pausing or cancelling it does not, even though both are at least as strong a signal that the
old offer shouldn't be honored. This is likely the single easiest fix that would close most of
finding #0's impact even before status checks are added to review/book.

### 1. [UX gap] Editing a request shows no indication the displayed total is now stale

**Found**: live test (PATCH budget_inr on request 1, then re-fetched observations - the
latest observation was unchanged, still showing the pre-edit total, with no flag).

**What happens**: `PATCH /api/requests/{id}` updates the request's fields and clears any
held offer (`_invalidate_stale_offers`), but never touches existing `PriceObservation` rows
(by design - they're historical/append-only) and never triggers a new check. The Dashboard
keeps showing the last observation as if it were still accurate.

**Why it's a real problem, not just "working as designed"**: if adults/rooms/dates change,
the old total was computed for the *old* occupancy/dates and is now actively wrong for the
edited request - but nothing on screen says so. A user has no way to tell "this total
reflects the trip as it used to be" from "this total reflects the trip as it is now"
without separately checking the edit timestamp against the observation timestamp (which
isn't shown either).

**File(s)**: `backend/app/routers/requests.py` (`update_request`), `frontend/src/pages/Dashboard.tsx`
(`ObservationSummary` - no staleness check against the request's own last-updated time, which
doesn't even exist as a tracked field).

### 2. [Real bug / safety gap] "Cancel" is irreversible, has no confirmation, and sits directly next to "Pause"

**Found**: live test - clicked "Cancel" on a request with no prompt; it was instantly and
permanently cancelled. `POST /{id}/reactivate` explicitly rejects moving a cancelled request
back to active (`"A cancelled request cannot be reactivated."`), so there is no recovery path
at all once this is clicked - not even through another part of the UI.

**Why this matters**: "Cancel" sits in the same button row as "Pause", "Resume", and "Edit" -
all reversible, all low-stakes. A single misclick (easy - they're adjacent, same size, same
styling) permanently kills a request, with the only recovery being direct database access,
which a real user would never have. Nothing in the project's own standing rules requires
destructive actions to be silently instant like this - the same project's git-safety
discipline (never force-push without asking, etc.) isn't reflected in its own product's UI.

**File(s)**: `frontend/src/pages/Dashboard.tsx` (`handleStatusChange` - no `confirm()` or modal
before the `cancel` action specifically, unlike how a real product would gate an irreversible
action).

### 3. [Real bug, systemic] Every backend validation error is shown to the user as raw JSON + HTTP status text

**Found**: live test - submitted a request with equal outbound/return dates (passes the
browser's `min` attribute since it's inclusive, correctly rejected server-side). The page
displayed: `400 Bad Request: {"detail":"Return date must be after the outbound date (got
outbound 2026-12-30, return 2026-12-30)."}` verbatim, in the red error box.

**Root cause**: `frontend/src/api.ts`'s shared `request()` helper does
`throw new Error(\`${response.status} ${response.statusText}: ${body}\`)` where `body` is the
raw (often JSON) response text - never parsed or made human-readable. Every single page's
catch block (`RequestForm.tsx`, `OfferReview.tsx`, `BookingResult.tsx`, `Dashboard.tsx`, `Ops.tsx`
- all of them) does `err instanceof Error ? err.message : '...'`, so this raw string is what
every single user-facing error message in the entire app actually looks like. This isn't one
page's bug - it's the one shared error path the whole app relies on.

**Impact**: a real backend validation message (which is itself well-written - "Return date
must be after the outbound date...") is buried inside "400 Bad Request: {"detail":"...` noise,
making every error in the product look like a raw server crash to a non-technical user,
regardless of how good the underlying message is.

**File(s)**: `frontend/src/api.ts` (`request()`), and by extension every page's error-display
code.

### 4. [Real bug] Scenario Lab buttons give zero loading feedback, and nothing stops a double-click

**Found**: live test - clicked "Run cycle now" and checked the result message after 800ms; it
hadn't updated yet (a real monitoring cycle against 3 active requests makes real Sabre/
Hotelbeds calls per request, ~10-15s each per earlier testing - confirmed correct after
waiting the full ~15s). Initially logged as a false positive, then re-verified and reclassified
once the actual cause (test wait time, not app bug) was found - noted here as process, not as
the finding itself.

**The real finding**: every button on the Lab page (`Move clock forward`, `Run cycle now`,
`Set override`, `Schedule this failure`, `Schedule this cancellation failure`,
`Schedule this restart`, `Reset everything`) has no `disabled={...}`/loading state at all,
unlike the rest of the app (`Dashboard.tsx` tracks `checkingId`, `RequestForm.tsx` tracks
`submitting`, `OfferReview.tsx` tracks `booking`/`reReviewing`). "Run cycle now" specifically
can take many seconds for real supplier calls across every active request - nothing stops a
user from clicking it again mid-flight, which would kick off a second overlapping real
monitoring cycle, spending real Hotelbeds/Sabre quota unnecessarily - directly against this
project's own stated discipline of not wasting scarce real quota.

**File(s)**: `frontend/src/pages/Lab.tsx` - every `handle*` function lacks a loading-state
guard.

### 5. [Real bug, spec compliance] The notifications list doesn't show itinerary/total/quote status — only a repeated generic label

**Found**: live test - a request with 3 separate alerts over time showed three cards that are
visually and textually identical except the timestamp: `Request #1 [NEW]` / `Open to review
the current price →`, three times in a row. No price, no route, no quote status anywhere in
the list.

**This is a direct spec gap, not just a nice-to-have**: Sec. 07 says the notification should
"Include itinerary, itemized total, observation time, quote status and a Review & book
action." Observation time is shown; itinerary, itemized total, and quote status are not -
and the backend doesn't even return enough to show them without an extra fetch per card:
`GET /api/notifications` (`NotificationOut`) only returns `observation_id`, not the
observation's own fields.

**Impact**: a user with more than one alert (exactly the real scenario just reproduced) has no
way to distinguish them at a glance - which one is the cheap one, which trip each belongs to,
whether the price already looks worth opening.

**File(s)**: `backend/app/schemas.py` (`NotificationOut` - no embedded observation summary),
`backend/app/routers/notifications.py` (`list_notifications` - returns raw `Notification` rows,
never joins in the observation), `frontend/src/pages/Notifications.tsx` (renders only
`request_id` and timestamps, has nothing richer to render even if it wanted to).

### 6. [Critical] The Scenario Lab's price override doesn't make a demo actually deterministic — it still depends on the real supplier call succeeding

**Found**: code read, `backend/app/pricing.py::build_package`. The package's overall `status`
("complete"/"unavailable") is computed from `flight["status"]`/`hotel["status"]`/`cab["status"]`
- the **real** statuses returned by the real Sabre/Hotelbeds calls, which `build_package`
*always* makes regardless of whether an override is set. An active override only substitutes
the *price number* afterward (`_apply_override`) - it never touches the status, and never
skips the real call.

**The concrete failure mode**: set a hotel price override on a request, intending a repeatable
below-budget demo. If the real Hotelbeds call for that check *also* happens to fail
(confirmed to happen in practice - see the "unavailable" investigation this session), the
whole package still comes back `status: "unavailable"`, `total_price: null` - the override
price is computed into `hotel_total_price` but never reaches the total, and no alert can ever
fire. The override did nothing useful at the exact moment it was needed most.

**This directly contradicts the Lab's own UI copy** (written in V5/V6, not noticed until this
read): *"Makes the target request's next price check use a price you choose, **instead of
calling the real supplier**."* That's not what happens - the real call still happens, and its
real outcome can still silently override the override.

**Why this is Critical, not just a real bug**: Sec. 11 explicitly requires "deterministic
fixtures... Reviewers must be able to reset and replay each case without waiting for real
market movements." An override that only works *when the real supplier happens to cooperate
anyway* is not deterministic - it's exactly the kind of flakiness Sec. 11 says this tooling
exists to eliminate. This plausibly explains at least some of the earlier "everything's
unavailable" experience, if a price override was in play at the same moment a real Hotelbeds
call failed.

**File(s)**: `backend/app/pricing.py` (`build_package` - status computed from real source
results regardless of override state; should treat an overridden component as "complete" and
skip its real call, or at minimum force its status) - `backend/app/sources/flights.py`,
`hotels.py`, `cabs.py` (never consulted before making their real call).

### 7. [UX gap] The Ops timeline collapses a booking's whole lifecycle into one entry showing only its current status

**Found**: code read, `backend/app/routers/ops.py::request_timeline`. A `BookingAttempt` row
is inserted once (`created_at` set then) and updated in place for every subsequent state
change (restart-resume, reconcile, compensation) - the timeline builds exactly one event per
booking row, at its original `created_at`, describing whatever its status happens to be *at
query time*. A booking that went pending → in_progress (crashed after flight) → resumed →
confirmed shows up as a single "Booking attempt: confirmed" line - the crash and resume moments
that Sec. 10's own "show what requires action" framing is supposedly there to surface are
invisible after the fact, even though they really happened and were real, interesting events.

**File(s)**: `backend/app/routers/ops.py` (`request_timeline` - one event per `BookingAttempt`
row, not one per actual state transition; there's no transition log to draw from, since
`booking.py` updates columns in place rather than appending history).

### 8. [Minor] Trip Story re-applies the request's *current* min-star filter to an old observation's raw data, not the filter that was active when the check actually ran

**Found**: code read, `backend/app/routers/story.py::get_trip_story` →
`app/story.py::extract_hotel_candidates(hotel_raw, trip_request.min_star_rating)`. If a user
edits `min_star_rating` after a check has already run, the Trip Story view re-filters that
check's raw hotel list using the *new* value, not whatever was in effect when the observation
was created and its `hotel_total_price` was actually picked. If the edit raises the star
requirement past whatever hotel was actually picked, that hotel silently drops out of the
candidate list entirely and nothing on the page ends up marked "Picked" for hotels, even
though the stored price is real and correct.

**File(s)**: `backend/app/routers/story.py` (uses `trip_request.min_star_rating` - the live,
current value - instead of a filter value captured per-observation).

### 9. [Test-coverage gap] No test anywhere checks that a paused or cancelled request can't be reviewed or booked

**Found**: searched `backend/tests/*.py` for any test exercising request status against
review/booking - none exists. `test_ownership.py` checks cross-*user* access on review/book;
nothing checks same-user access against a non-`active` request. This is exactly the gap that
let finding #0 ship across five versions (V1-V6) with 39 passing tests the whole time -
"tests passing" was never evidence this particular path was safe, because nothing tested it.

**File(s)**: `backend/tests/test_booking.py`, `backend/tests/test_ownership.py` - the fix for
finding #0 should ship with a same-user, non-active-status test alongside it, not just the
status-check code itself.

### 10. [Minor] A cancelled request can still be freely edited, even though it can never be reactivated

**Found**: code read + live test. `update_request` has no status check either - a cancelled
request's origin/destination/dates/budget/etc. can all still be changed via the UI's Edit
form. But `reactivate_request` explicitly refuses to bring a cancelled request back to
`"active"`. So editing a cancelled request is real, saveable, and completely inert - the
edited values can never again drive a real check, since the request can never become active
again. The Dashboard shows an "Edit" button unconditionally, with no indication this is the
case.

**File(s)**: `frontend/src/pages/Dashboard.tsx` (Edit link has no status-based condition, unlike
Pause/Resume/Cancel which are correctly conditional), `backend/app/routers/requests.py`
(`update_request` - no status check, consistent with the same gap as finding #0 but lower
severity since nothing harmful results, just a dead-end action).
